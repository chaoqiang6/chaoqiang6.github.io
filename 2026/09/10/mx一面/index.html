Q: 自动化部署平台是如何支持多版本的？

A: 我们主要通过“不可变制品 + Helm Release + 流量路由”来支持多版本。
首先，每次构建都会生成带有唯一版本号的镜像和 Helm Chart，例如镜像使用 service:1.0.1，Chart 也有对应版本，并将版本信息记录在 Git 配置文件中。
发布时，Jenkins 流水线接收目标集群、环境、服务和版本号等参数，读取配置后部署指定版本。不同版本不会覆盖同一个运行实例，而是创建独立的 Deployment 或 Helm Release，并通过 app、version 等 Label 进行区分。
如果只需要升级，可以直接对原 Release 做滚动升级，并支持 Helm 回滚。如果需要多个版本同时运行，例如灰度发布，则分别创建新旧版本对应的 Service，再通过 Ingress、网关或 Service Mesh 按比例分发流量，例如旧版本 90%、新版本 10%。
灰度期间结合监控指标观察错误率、响应时间和业务数据，确认新版本稳定后逐步扩大流量；如果出现问题，就把流量切回旧版本并执行回滚。调整流量比例只修改路由配置，不需要重新发布网关服务。

Q:讲一下MVCC
A:数据库的multi-version concurrency control 多版本并发控制，主要解决数据库读写冲突,让读操作尽量不阻塞写操作
具体实现方式是innodb会在记录中维护事务id，通过undo log保留数据的旧版本
查询时生成readview
普通查询不加锁
写操作会读取当前的版本
可以理解为数据库不急着覆盖旧数据，而是暂时保留多个版本，让不同事物读取到它应该看到的版本，
同一行数据保存多个版本快照，读操作不加锁，读到合适版本；写操作创建新版本，以此实现读写不阻塞。
InnoDB 的 MVCC 是为了解决：读不加锁，读写不冲突，提升并发性能。
