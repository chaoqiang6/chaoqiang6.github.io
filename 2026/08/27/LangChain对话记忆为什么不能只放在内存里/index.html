内存记忆的问题

本地 demo 里把历史消息放进一个 list 很方便，但服务一旦多实例部署，请求下一次可能被路由到另一台机器。进程重启后，用户的对话也全部消失。

这段代码只能用于单进程实验。生产环境至少要定义会话 id、过期时间、最大消息数和存储位置。

Redis 保存摘要

对话越长，发送给模型的 token 越多，成本和延迟都会增加。可以保留最近几轮消息，把更早内容压缩成摘要，再一起放入 prompt。

Redis 列表只是一个简单示例。真正上线还要考虑并发写入顺序、序列化格式、敏感信息清理和用户注销时的数据删除。

记忆不是事实库

模型上下文中的历史对话只是辅助信息，订单状态、余额和权限仍然应该实时查询可靠系统。不能因为模型“记得”用户说过什么，就把这段文字当作业务事实。

这里和缓存设计很像：记忆可以改善体验，但必须有容量、过期和一致性边界。
